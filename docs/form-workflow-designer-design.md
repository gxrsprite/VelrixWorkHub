# 自定义表单与可视化流程设计

状态：设计基线，暂不进入开发。本文用于固定后续 Form、Workflow、Canvas 和 Blazor 前端的边界；实现时允许细化 DTO 与表结构，但不得绕过本文的安全、版本和权限原则。

## 1. 目标与范围

目标是让业务人员通过表单设计器和流程设计器完成一类业务的定义：表单负责采集和展示数据，流程负责节点、参与人、条件、流转和动作，运行时根据当前节点和当前登录用户生成可操作页面。

首个完整版本需要支持：

- 从控件目录向表单添加基础控件、组织控件、业务控件、审批控件和自定义表格。
- 配置字段、表格列、行操作以及节点操作的可见、只读、可编辑和必填权限。
- 用户、角色、部门等选择控件具有独立的数据范围，不能因为用户能编辑字段就自动获得选择全部组织数据的权限。
- 流程在 Canvas 上配置开始、审批、人工处理、条件分支、业务动作、通知、回退、受控循环、取消和结束。
- 已发布表单和流程不可变；运行实例固定启动时的表单版本、流程版本和快照。
- 表单和流程定义不允许包含任意 C#、JavaScript、SQL 或反射字段写入。

暂不在第一阶段支持：任意脚本控件、用户上传前端组件、任意 SQL 数据源、跨实例分布式事务、无限循环、嵌套自定义表格，以及运行中实例自动迁移到新版本。

## 2. 核心边界

```text
设计态
  Form Designer (Blazor) ────────> FormDefinitionVersion
  Workflow Canvas (JS Adapter) ──> WorkflowDefinitionVersion

发布态
  已发布表单版本 + 已发布流程版本 + 控件/动作目录版本

运行态
  Blazor Form Renderer
       │
       ├─ FormRuntimeDescriptor：字段值、字段权限、可选数据范围
       ├─ WorkflowRuntimeDescriptor：当前节点、任务、可执行动作
       └─ Runtime Command：保存、提交、同意、拒绝、回退、取消等
                │
          Workflow Engine
                │
       Business/Form Action Adapter
```

Form 和 Workflow 分开建模：

- Form 只描述字段、控件、布局、校验、表格和数据绑定。
- Workflow 只描述节点、连线、条件、参与人、权限策略和动作。
- 节点通过 `FormPolicy` 引用表单中的稳定字段 ID/Key，不能复制一份表单定义到节点配置中。
- Canvas 供应商 JSON 不是服务端合同；服务端只保存稳定的 `WorkflowDefinitionDocument`。

## 3. 表单定义模型

### 3.1 定义与版本

- `FormDefinition`：稳定身份、编码、名称、业务范围和当前版本信息。
- `FormDefinitionVersion`：不可变发布单元，包含控件树、布局、字段、校验、数据源引用和默认权限。
- `FormFieldDefinition`：字段稳定 ID、稳定 Key、名称、数据类型、控件类型、默认值、校验规则和绑定方式。
- `FormLayoutNode`：页面、页签、分组、行、列、折叠区和字段的布局树。
- `FormTableDefinition`：自定义表格定义及列集合。
- `FormVersionStatus`：`Draft`、`Published`、`Archived`。

字段 ID 和 Key 发布后不得改变。修改显示名称、布局或控件配置必须创建新版本；条件表达式、权限策略和流程动作均引用稳定字段 Key。

### 3.2 数据模式

表单支持两种模式，但使用同一运行时渲染协议：

1. `DynamicForm`：全部业务数据保存在表单实例 JSON 中，适合完全自定义流程。
2. `BusinessBoundForm`：标准字段通过业务 Adapter 绑定 CRM/ERP/PMP 等领域对象，自定义扩展字段仍保存在扩展数据中。表单不能直接映射任意数据库列。

第一批全自定义流程优先使用 `DynamicForm`。现有业务模块迁移时使用 `BusinessBoundForm`，继续由业务 Adapter 校验和持久化领域字段。

## 4. 控件目录与扩展机制

控件不是一组散落的 Razor 组件，而是具有稳定类型键和版本的注册目录。每个控件定义至少提供：

- `ControlTypeKey` 和控件版本。
- 设计态配置 Schema、运行态数据 Schema 和默认配置。
- 支持的数据类型、校验器和格式化器。
- Blazor 设计态组件、运行态编辑组件和只读组件。
- 可选项解析器、数据权限解析器和序列化策略。
- 是否允许放入自定义表格列，以及表格内的限制。

计划中的控件类别：

| 类别 | 控件示例 | 关键约束 |
|---|---|---|
| 布局 | 标题、说明、分组、页签、折叠区、分隔线、栅格列 | 不保存业务值 |
| 基础输入 | 单行文本、多行文本、数字、金额、日期、日期时间、开关、单选、多选 | 服务端重复执行格式和范围校验 |
| 文件内容 | 附件、图片、富文本 | 复用附件权限；富文本必须净化 |
| 组织选择 | 用户、角色、部门、岗位/成员范围 | 选项由服务端按当前用户数据范围过滤 |
| 业务选择 | 客户、供应商、商品、项目、合同、订单等 | 通过注册数据源查询，不直接跨模块查表 |
| 计算展示 | 公式、汇总、编号、状态标签、只读文本 | 使用安全表达式和注册函数 |
| 流程审批 | 发起人、当前节点、审批意见、审批历史、抄送信息、审批操作栏 | 仅在流程运行上下文中可用 |
| 命令 | 保存草稿、提交、业务命令按钮 | 只能调用已注册命令，不能配置脚本 |
| 明细数据 | 自定义表格 | 列使用受限控件目录，行具有稳定 ID |

允许后续开发新的内置控件，但不允许业务用户上传并执行自定义 JavaScript。确需特殊前端交互时，由开发侧注册受信任控件包，并为其配置 Schema、权限、验证和版本兼容策略。

## 5. 自定义表格

自定义表格是一级控件，不是简单的 JSON 文本框。其定义包含：

- 稳定 `TableKey`、标题、最小/最大行数和默认空行策略。
- 列定义：稳定列 Key、控件类型、宽度、固定列、排序、格式、默认值和校验。
- 表格操作：新增行、复制行、编辑行、删除行、批量选择、导入和导出。
- 节点权限：表格整体权限、列权限、行操作权限和可选的行条件。
- 公式与汇总：行内公式、列汇总、跨列校验和表单字段引用。
- 选项数据源：用户、角色、部门、字典和业务对象等注册数据源。

每行生成稳定 `_rowId`，流程回退、再次编辑和审计差异都通过 `_rowId` 识别原行，不能依赖数组下标。

表格列复用普通字段的控件与验证协议，但第一阶段禁止表格嵌套表格、在单元格中放审批操作栏，以及使用不能稳定序列化的复杂编辑器。

选择类表格列需要同时配置两种权限：

- 字段操作权限：当前节点的当前用户能否查看或修改该单元格。
- 选项数据权限：该用户可以选择哪些用户、角色、部门或业务对象。

例如“负责人”列允许审批人编辑，并不表示审批人可以选择全公司用户；可选范围仍可限制为当前部门、指定角色成员、表单中已选择部门的成员或某个注册组织范围。

## 6. 节点级表单权限

每个可交互节点配置 `FormPolicy`，包括字段策略、表格策略和运行时动作策略。

### 6.1 权限主体

权限规则可引用：

- 发起人、当前任务审批人、流程管理员。
- 指定用户、角色、部门和部门负责人。
- 表单字段中选择的用户、角色或部门。
- 上一节点处理人、业务对象负责人。
- 由注册参与人解析器计算出的人员集合。

所有主体最终解析为当前登录用户是否匹配；查询参数、表单隐藏值和浏览器传入的用户名不能作为操作者身份。

### 6.2 字段状态

运行时字段状态为：

- `Hidden`：服务端运行时描述中不返回值，提交时也不接受该字段。
- `ReadOnly`：可以显示，客户端提交的修改会被拒绝。
- `Editable`：允许修改，仍需通过类型、格式、业务和数据范围校验。
- `EditableRequired`：允许修改且当前节点完成前必须有有效值。

权限解析遵循以下顺序：

1. 系统安全策略和敏感字段策略优先。
2. 判断当前用户是否有查看权限；没有则为 `Hidden`。
3. 判断用户是否持有当前节点的有效任务或节点授权；没有则最多为 `ReadOnly`。
4. 匹配节点字段规则；显式禁止编辑优先于允许编辑。
5. `Required` 只对可编辑字段生效；发布校验必须确保必填字段至少有一个合法编辑主体。

权限既用于生成前端控件状态，也必须在保存、提交和审批命令中由服务端重新计算。禁用按钮、只读输入框和隐藏 CSS 不是安全边界。

### 6.3 表格权限

表格权限分为四层：表格可见性、列可见/编辑、行新增/删除/复制、特定行的条件权限。服务端按 `_rowId` 对提交差异进行校验，拒绝修改无权编辑的列、删除无权删除的行或伪造新的组织引用。

## 7. 审批相关控件与按钮

审批控件只在 `WorkflowRuntimeContext` 中启用：

- `ProcessSummary`：流程状态、发起人、开始时间和当前节点。
- `ApprovalOpinion`：当前任务的审批意见输入。
- `ApprovalHistory`：节点、处理人、动作、意见、时间和轮次历史。
- `WorkflowActionBar`：保存、提交、同意、拒绝、回退、转交、加签、抄送、撤回、取消等操作。
- `CurrentAssignees`：当前节点处理人和待处理状态。

`WorkflowActionBar` 不保存设计者任意填写的按钮命令。服务端根据流程状态、任务归属、节点策略和当前用户返回 `AvailableActions`，Blazor 只渲染允许的动作。每次执行仍由服务端验证任务状态、Actor、实例版本、并发版本和幂等键。

普通命令按钮也只能引用注册命令，例如“计算报价”“生成订单”“同步项目”，并声明输入字段、输出字段、权限意图和是否允许在当前节点调用。

## 8. 可视化流程模型

目标节点类型包括：

- `Start`：唯一开始节点。
- `Approval`：产生一个或多个审批任务。
- `ManualTask`：需要处理人填写或修改表单，但不要求审批结论。
- `Condition`：根据安全表达式选择分支。
- `ParallelSplit` / `ParallelJoin`：并行分支与汇合。
- `Notification`：站内通知及后续可插拔渠道。
- `BusinessAction`：调用已注册动作，例如设置字段、创建业务对象或发布事件。
- `SubProcess`：调用已发布子流程，后期实现。
- `End`：正常完成。
- `CancelEnd`：取消并终止实例。

连线需要稳定 ID，并包含 `TransitionKind`、条件、优先级、是否默认分支和目标节点。条件节点必须具有唯一默认分支，其他分支按优先级求值，条件不得执行任意代码。

### 8.1 回退、拒绝与重新提交

- `Reject`：按节点策略终止实例或进入配置的拒绝目标节点。
- `ReturnToPrevious`：回到本轮实际经过的上一个人工节点。
- `ReturnToNode`：回到设计时声明的可回退节点。
- `Withdraw`：发起人在允许阶段撤回到发起节点。
- 回退不会删除历史节点执行记录；引擎创建新的 `NodeExecution` 和轮次，旧任务保持已结束状态。
- 回退后哪些字段可编辑由目标节点自己的 `FormPolicy` 决定。

### 8.2 循环

现有“禁止任何环路”的校验需要在后续引擎版本中调整为“禁止无界环路”。允许循环必须满足：

- 连线显式标记为 `Loop`，或通过专用循环节点表达。
- 配置最大迭代次数，必要时配置超时、人工退出或默认退出分支。
- 每次经过节点都创建新的执行轮次，任务、表单修订和动作保持可追溯。
- 超过上限时实例进入异常等待处理状态，不能继续自动执行。
- 发布校验拒绝没有退出路径、没有上限或纯自动节点构成的高风险忙循环。

## 9. 运行时数据与审计

建议的核心运行态对象：

- `FormInstance`：表单定义/版本、业务绑定、当前数据和修订号。
- `FormRevision`：保存或节点提交产生的不可变修订，记录字段和表格行差异。
- `WorkflowInstance`：流程定义/版本、表单实例、状态、当前执行令牌和快照。
- `NodeExecution`：某节点某次进入的执行记录，包含轮次、进入/离开时间和结果。
- `WorkflowTask`：分配给用户的人工任务，必须关联 `NodeExecutionId`。
- `WorkflowActionLog`：动作、Actor、输入摘要、输出摘要、幂等键和失败信息。

表单当前值使用统一 JSON 约定保存，枚举使用名称字符串，中文保留原文。引用值保存稳定 ID，并在修订或审计中保留必要的显示快照。例如用户选择保存用户 ID，显示名仅作为快照，不作为权限判断依据。

自定义表格按数组保存，每行含 `_rowId`。查询频繁的关键字段后续通过受控索引定义投影到查询索引表，不能让设计者输入 SQL 或数据库列名。

## 10. 表单运行时协议

服务端按当前用户、实例和节点生成 `FormRuntimeDescriptor`：

- 表单版本、布局和控件描述。
- 当前可见字段值和表格数据。
- 每个字段、表格、列和行操作的最终权限。
- 选择控件的数据源令牌、过滤上下文和分页能力。
- 当前节点、任务信息、审批历史摘要和 `AvailableActions`。
- 并发修订号、任务版本和命令幂等令牌。

提交命令只携带发生变化的字段/表格差异、修订号和动作。服务端重新加载实例和当前用户权限，验证差异后保存修订，再由流程引擎决定是否流转。前端不能直接指定下一个节点或把字段权限随请求传回服务端作为可信结果。

## 11. Blazor 与 JavaScript 技术决策

采用混合方案：Blazor 是应用主体，JavaScript 图编辑库只负责 Workflow Canvas。

### 11.1 由 Blazor 实现

- 表单设计器页面框架、控件目录、属性面板、版本管理和发布校验结果。
- 表单运行时渲染、字段组件、自定义表格、数据选择弹窗和审批操作栏。
- Canvas 外围工具栏、节点属性面板、表单权限配置和保存/发布命令。
- 所有权限、校验、条件编译、流程执行、业务动作和审计。

表单布局拖拽优先使用 Blazor 组件；必要时只引入很薄的排序/拖拽辅助模块，不建立第二套前端状态管理。

### 11.2 由 JS Canvas 适配器实现

- 节点拖动、连线、缩放、平移、框选、对齐线、快捷键和小地图。
- Canvas 内部选中态和高频指针事件。
- 供应商图模型与稳定 `WorkflowDefinitionDocument` 的双向转换。

Canvas 的 DOM 子树由 JS 图编辑器独占，Blazor 不在同一子树内增量渲染节点，避免双方同时修改 DOM。JS 不能执行条件或业务动作，只能编辑和展示定义。

JS Interop 使用隔离模块，边界保持粗粒度：

- `initialize(container, document, readonly)`
- `loadDocument(document)` / `exportDocument()`
- `setReadonly(value)` / `focusNode(nodeId)`
- 向 .NET 发送经过节流的 `selectionChanged`、`documentChanged` 和 `commandRequested`。

当前 Web 使用 Interactive Server，不能把每次鼠标移动都通过 SignalR 发送给 .NET。图形状态留在浏览器内，高频交互在 JS 内完成；属性确认、结构变更和保存时才同步。较大的完整 Workflow JSON 使用独立保存 API 或受控增量协议，不依赖大量细碎 JS Interop 调用。

### 11.3 图编辑库选择

首选对框架无绑定、支持节点/边 JSON、SVG/HTML 节点和插件扩展的图编辑引擎；当前候选优先级为：

1. X6：优先验证，适合通用图编辑，能够独立使用，不要求引入 React/Vue。
2. LogicFlow：作为流程图场景的备选，同样通过内部 Adapter 隔离。
3. React Flow：功能成熟，但它本身是 React 组件；除非后续决定维护 React Island，否则不作为 Blazor 项目的首选。

最终库选择必须经过小型技术验证：节点/边导入导出、复杂图性能、只读模式、快捷键、分组/并行节点、销毁重建、Blazor Server 断线恢复和许可证审查。无论选择哪一个，持久化格式和 Application 契约都不得依赖供应商类型。

前端依赖必须随应用本地构建和部署，不从公共 CDN 动态加载。

## 12. 发布校验

表单发布前至少校验：

- 字段 Key、表格 Key 和列 Key 唯一且稳定。
- 控件类型和控件版本已注册，配置符合 Schema。
- 默认值、公式、校验和数据源类型兼容。
- 组织/业务选择器的数据范围配置有效。
- 必填字段在需要完成的节点中存在合法编辑主体。
- 表格不包含禁用控件、非法嵌套或无界行数配置。

流程发布前至少校验：

- 开始/结束、节点可达性、连接端口和分支默认路径完整。
- 参与人解析器、表单字段引用、条件字段类型和动作均已注册。
- 自动节点链存在步数限制，循环有明确上限和退出路径。
- 回退目标合法，不跳入不可恢复的并行分支内部。
- 并行分支与汇合策略匹配。
- 节点字段权限不会造成“必填但无人可编辑”。
- 审批节点至少能解析出一种合法审批人来源。

发布校验在服务端执行；Canvas 和表单设计器的即时提示只用于改善体验。

## 13. 安全与审计原则

- 不支持任意 JavaScript、C#、SQL、URL 回调和反射属性路径。
- 条件、公式和参与人规则使用受限表达式语言，只允许白名单运算符和注册函数。
- 用户、角色、部门和业务数据源均由服务端执行数据范围过滤。
- 隐藏和只读字段不依赖客户端保护；提交时重新计算权限并校验差异。
- 富文本、HTML 展示和附件预览需要净化和内容安全策略。
- 审批 Actor 始终来自当前登录用户，任务 ID、审批人和可执行动作由服务端复核。
- 所有节点进入/离开、字段差异、表格行差异、审批意见、转交、回退、循环轮次和业务动作均进入审计。

## 14. 版本与兼容

- 草稿可编辑；发布版本不可修改，只能复制为新版本。
- 新启动实例使用最新有效发布版本；运行中实例继续使用启动快照。
- 控件、数据源、参与人解析器和业务动作都有稳定 Key 和兼容版本。
- 删除控件实现前必须确认没有发布版本引用；旧版本所需渲染器必须保留。
- 第一阶段不自动迁移运行实例。未来如增加迁移，只允许显式、可预览、可回滚的版本迁移方案。

## 15. 分阶段实施建议

1. 固定 Form Definition、Runtime Descriptor、权限策略、表格和控件目录合同。
2. 实现只读/编辑运行时渲染器、动态表单数据和服务端权限校验。
3. 实现 Blazor 表单设计器，包括基础控件、组织选择器和自定义表格。
4. 通过 JS Adapter 接入 Canvas，先支持无环的开始、审批、条件、动作和结束。
5. 扩展回退、撤回、取消、受控循环、并行和子流程。
6. 接入现有 OA/CRM/ERP/PMP 业务 Adapter，并逐步替换手工状态流转。

每阶段都先完成稳定 JSON 合同、发布校验和自动化测试，再开放设计器 UI。

## 16. 已确定与待验证事项

已确定：

- 表单与流程分开版本化，实例分别保存不可变快照。
- Blazor 负责应用和表单，JS 图编辑器仅负责 Canvas。
- 不引入完整 React/Vue 子应用作为流程设计器。
- 字段权限、选项数据范围和审批动作必须由服务端计算。
- 自定义表格拥有稳定行 ID、列级权限和独立选项数据范围。
- 循环必须显式、有限并保留每轮执行历史。

进入开发前仍需通过技术验证确定：

- X6 与 LogicFlow 的最终选择及前端打包方式。
- 安全表达式语言的语法、函数目录和调试体验。
- 富文本编辑器、超大表格虚拟化和单实例数据量上限。
- 动态表单字段的查询索引方案。
- 并行审批的会签、或签、超时和撤销规则。
